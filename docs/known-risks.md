# Known Risks

- The Switch service currently exposes one CMIF command that carries the versioned binary envelope in alias buffers; larger future config payloads may require chunking or a larger negotiated buffer budget.
- Tesla overlay work is intentionally deferred from Phase A; the overlay target remains a host stub.
- Tesla live toggling through hard-kill tools such as `pmshellTerminateProgram()` / `pmshellLaunchProgram()` is unsafe for MITM-enabled packages because it can bypass Atmosphere `UninstallMitm`; use SWG's `RequestShutdown` control path before restarting the sysmodule.
- The Switch manager is the current Phase A control UI; it is text-mode and intentionally simpler than the future Tesla UX.
- The new Switch integration app now exposes a one-button end-to-end harness for `ResolveDns()`, `SessionSocket`, `TunnelDatagramSocket`, and `TunnelStreamSocket`, but it still needs hardware validation against a real routed test host.
- The normal `switch-debug` package now enables the Atmosphere MITM observer and actively owns `sfdnsres`. It expects `atmosphere!enable_dns_mitm=false` so Atmosphere's built-in DNS MITM frees the service; if Atmosphere still owns it, SWG logs `0x815 (module=21, description=4)` and cannot replace it.
- MITM ownership is explicitly uninstalled on graceful sysmodule exit through Atmosphere command `65001`. If a previous build or external stop tool hard-killed the sysmodule without uninstalling, Atmosphere will keep that stale owner until reboot because a new process id is not allowed to uninstall another process's MITM.
- The active DNS replacement is now hardware-validated for ownership, Moonlight resolver session acceptance, and graceful uninstall. Telemetry-host resolution still needs a direct verification pass before treating SWG as a complete Atmosphere DNS MITM replacement.
- The current DNS MITM replacement preserves Atmosphere telemetry blocking and hosts-file behavior, but it does not yet answer arbitrary DNS through the WireGuard tunnel. Tunnel-backed transparent DNS remains the next resolver slice.
- Milestone 5 implementation now covers one-shot WireGuard initiation/response, authenticated transport send/receive, repeated host-side traffic, and bounded reconnect on outbound send, receive-loop, and periodic keepalive transport failures, but cookie replies and rekeying are still not implemented.
- The protocol and crypto implementation now comes from `third_party/wireguard-lwip`, which reduces local protocol-bug surface but adds submodule maintenance, license tracking, and upstream-audit responsibility.
- The local adapter preserves SWG's existing exact-payload authenticated transport semantics. Upstream's lwIP interface pads inner IP packets to 16-byte boundaries; if the SDK packet channel becomes strictly IPv4-only, padding and post-decrypt length trimming should be revisited deliberately.
- The current Switch tunnel session preparation is intentionally IPv4-only: hostname endpoints are left unresolved for a later resolver/UDP slice, IPv6 endpoints are rejected, and IPv6 routes or DNS entries are only tracked as skipped metadata.
- The live connect path now resolves IPv4 endpoints, validates the handshake, schedules authenticated keepalives, and surfaces authenticated transport send/receive through `swg:ctl`; host regression coverage now repeats multi-packet app-session traffic and scripted reconnect triggers, but there is still no endpoint roaming support.
- `RecvPacket` is currently session-gated rather than per-app demultiplexed; multiple consumers on the same connected profile would compete for one bounded queue until a richer socket/session model exists.
- `SendPacket` and `SessionSocket` are still packet-channel helpers rather than Moonlight-ready socket abstractions; Moonlight-facing UDP and TCP integrations should use `TunnelDatagramSocket` and `TunnelStreamSocket` instead.
- The new host live-handshake probe can separate protocol and remote-peer issues from Switch-specific networking behavior, but a host success still does not prove that Horizon BSD behavior or on-device UDP reachability is identical.
- BSD startup still depends on Horizon service behavior that can differ by firmware and sysmodule context; the runtime now logs staged diagnostics on failure, and the current hardware baseline confirms the normal query-only `bsd:u` hook does not destabilize Moonlight.
- The current Switch heap budget is 4 MiB so BSD can allocate its `0x234000` transfer-memory block with headroom; future WireGuard packet pools or transparent-mode buffers may require retuning that heap size.
- The authenticated WireGuard receive queue is now large enough for short Moonlight-style media bursts, but it is still deliberately bounded (`256` packets / `512 KiB`). Higher bitrate streams or longer consumer stalls may still require retuning once on-device video runs are measured.
- Current Moonlight diagnostics now prove that HTTPS, RTSP, and ENet control traverse the tunnel and that Moonlight opens/polls both audio and video datagram handles, but neither media handle has received a matched payload yet. The new tuple-mismatch logs should show whether media UDP is missing entirely or arriving on the wrong source/destination ports; the root cause is still not fixed.
- Newer Moonlight diagnostics refined that picture further: audio now receives matched tunneled payloads, but video still times out empty. The current fix aligns the video datagram handle with the RTSP-advertised client port pair by reserving local UDP `50001`; that hypothesis still needs on-device confirmation.
- The `50001` local-port alignment was confirmed on-device but did not fix the missing video path. Inner IPv4 fragment reassembly did restore functional video, and newer `swg.log` traces then confirmed a second fragment-path limit under load: the old `8`-entry reassembly cap evicted media packets with `fragment entry limit` warnings, and even the later `128`-entry build still saturated on full-size orphan tail fragments. The current build raises the cap again to `256`, raises bounded fragment storage to `768 KiB`, and adds host coverage for a 192-packet `1408`-byte tail-first burst, but this still needs hardware confirmation against Sunshine.
- Functional connectivity is now present for video, audio, and control, but Moonlight quality is still not proven stable under sustained load. The current mitigation routes packets for already-open flows straight into per-flow pending queues instead of reusing the shared deferred backlog for every poll; this should reduce latency and backlog churn, but it still needs on-device validation against the `bad connection` warning and broken A/V playback.
- Current profiling now also points at a client-side CPU hotspot: the Switch poll shim calls `swg_compat_socket_wait(..., timeout=0)` from tight loops, and before this change every empty probe still performed a real tunnel `Receive()` on the caller thread. `sdk/src/compat_bridge_switch.cpp` now rate-limits empty zero-timeout probes with a `4 ms` backoff, but this still needs on-device confirmation against the `100%` main-core spike and may not be the only remaining hot path.
- The more important remaining CPU hypothesis is now packet rate, not just empty polls: before this change, tunneled media still paid one `RecvTunnelDatagram` control request per UDP packet. The new burst path reduces that to one bounded batch per compat-bridge queue fill, but this still needs on-device confirmation against the `100%` core spike and may need a similar batching or shared-buffer strategy for other hot paths if video CPU remains too high.
- A second receive-side overhead source is now addressed but not yet proven on hardware: before this change, even quiet UDP periods still caused the Moonlight process to issue repeated `ReceiveBurst` probes every `10 ms` while waiting through the normal `100 ms` socket timeout. Blocking datagram waits now happen inside the sysmodule instead, but stream/control paths still use app-side polling and packet serialization/copy costs may still be high enough to matter under active video.
- Attempting to split `swg:ctl` transport handles across threads proved too risky in practice for the current control path: the C++ `thread_local` variant caused an immediate host-open crash, and an explicit per-thread handle-cache variant then regressed stream start with `STAGE_RTSP_HANDSHAKE` failures. The current build is rolled back to the stable single-handle transport. Input latency therefore remains unsolved, and the next safer work area is the ENet wait/receive cadence in `sdk/src/enet_compat.cpp` and the remaining zero-timeout `StreamControl` probe rate in `sdk/src/compat_bridge_switch.cpp`, not further transport-handle fan-out.
- Even if the fragment-entry warnings disappear on the next hardware repro, the latest audio close summary still showed `pending_datagrams=187`, so a second consumer-side drain bottleneck may remain in the compat bridge receive/wait path under sustained video load.
- DNS servers currently need to be numeric IP literals during connect preflight; hostname-based resolver configuration is not accepted yet.
- Capability detection now probes live service reachability, but some flags still map to nearest current surfaces (`sfdnsres` for resolver reachability and `nifm:a`/`nifm:s` for network-configuration reachability) rather than final transparent-mode hooks.
- Current compatibility reporting still does not probe `bsd:u` or `bsd:s` directly, so any future socket MITM rollout needs a tighter service-availability check before activation.
- The `bsd:u` hook is query-only in the normal build and intentionally fails open. The manual `SWG_ENABLE_EXPERIMENTAL_BSD_MITM_ADAPTER_LAB` path routes tracked IPv4 UDP sockets through tunnel datagram handles, while policy-approved local/multicast IPv4 UDP and local IPv4 TCP are forwarded to the app's original BSD session. This lab path still needs hardware validation and tunneled TCP command adapters.
- The adapter-lab BSD MITM path has much larger per-session state than the query-only hook. Keep its server/session tables off the thread stack; a stack overflow here can crash HOS during sysmodule startup before the adapter-ready log line.
- The adapter-lab BSD MITM path shares tracked sockets, app-session state, and the preserved `RegisterClient` transfer-memory handle across cloned libnx BSD sessions. It asks the original `bsd:u` service to allocate socket fd numbers, including valid fd `0`, and now retains that original service as the direct backend instead of registering a second BSD client. Moonlight still needs hardware confirmation through `original=registered`, `direct_backend=original_bsd_forwarding`, and successful forwarded TCP/UDP operations.
- The latest Moonlight Curl trace proved the adapter build was current, but also exposed a TLS-reuse diagnostic trap: logging `Socket` input after a nested native BSD call could show CMIF response magic instead of the original socket arguments. The adapter now copies command payloads first, handles descriptor-only `fcntl` calls, and logs HIPC handle counts, but the pre-connect Curl command sequence still needs hardware confirmation.
- Active `bsd:u` replacement is now restricted to exact app-policy `title_id` values with `transparent_mode` requested. Launching Moonlight through Sphaira/hbloader exposes the homebrew host process at the HOS service boundary, so there is no safe per-`.nro` BSD distinction there; selecting that host can destabilize Sphaira and subsequent homebrew launches.
- The adapter-lab BSD MITM path no longer rewrites direct `GetSockName`, send/receive, or socket-option buffers through a private native socket. Forwarding those operations to the original service removes that copy boundary, but discovery, ping, close, video startup, and frontend reopen still need hardware confirmation.
- Mixed readiness sets containing both original-service sockets and SWG tunnel datagrams are still experimental. `dbg0715i` continues to use the existing adapter-owned readiness loop for mixed sets; that behavior must be hardened before broad transparent routing.
- Scheduler behavior is phase-adaptive in `dbg0715i`: setup uses ascending control-session priority and exact original-service waits, while the first successful MMsg enables round-robin scheduling, 1 ms direct Poll/Select slices, and forced `MSG_DONTWAIT` for direct UDP receives. This can increase short `EAGAIN` returns and request/CPU rate, so hardware testing must compare responsiveness and sustained packet milestones. The MMsg trigger is a Moonlight-derived heuristic; clients that begin high-rate traffic without MMsg remain in control-priority mode.
- Batched BSD messages are deliberately asymmetric in `dbg0715i`: original-service `RecvMMsg` is forwarded unchanged, while `SendMMsg` is forwarded only after a bounded parser validates `vlen <= 32`, the packed buffer stays within the adapter HIPC limit, every destination is supported IPv4, and every route decision is `Direct`. The packed data is expected in libnx's mapped receive descriptor, with exchange/receive-static/send fallbacks retained for ABI diagnostics. Tunnel-backed `SendMMsg`/`RecvMMsg` remain unsupported and fail with `EOPNOTSUPP`; implementing them requires a separate bounded batch tunnel API rather than forwarding around policy.
- The adapter still uses one worker to preserve the verified shutdown model. `dbg0715h` proved the RTSP repair reaches media, but its only worker was still blocked for `99086 us` by one direct UDP receive. `dbg0715i` bounds post-MMsg direct UDP receive and readiness work instead of introducing new ownership/threading risk. If media still stalls under sustained traffic, the next behavioral slice remains a small bounded worker pool plus explicit shared-state ownership; do not add one thread per libnx clone.
- The Poll ready-result repair is intentionally narrow but still replaces an unparseable original-service response. `dbg0715h` verified it restores the missing RTSP receive and reaches media. It applies only when the normal BSD response payload cannot be parsed, the complete Poll input and output arrays can be inspected, every input descriptor has zero `revents`, and at least one output descriptor gains nonzero `revents`. Keep its bounded evidence logged and do not generalize it to Select or other BSD commands without equivalent evidence.
- Port-48010 diagnostics classify only known RTSP method/status prefixes and byte counts. Encrypted, fragmented, or unrecognized traffic appears as `opaque`; the absence of a classification is not itself a protocol failure. Never expand this telemetry to dump RTSP payloads, URIs, headers, credentials, session tokens, or key material.
- The previous manager-stop crash reproduced the same `bsdsocket` user-break signature after the adapter's private BSD runtime had initialized. `dbg0714a` removed that runtime from the direct path, and its hardware test completed all adapter and hook-uninstall stages without a crash. `dbg0715i` retains the fail-safe that refuses process exit if a MITM worker remains alive; that emergency path deliberately parks the sysmodule until reboot.
- Config validation checks presence and basic ranges, not cryptographic key or CIDR correctness.
- The app API now includes policy-safe DNS responses plus real UDP and TCP tunnel handles, but the tunnel DNS path is still limited to synchronous IPv4 A-record lookups and HTTPS still needs TLS or HTTP handling layered above `TunnelStreamSocket`.
- The passive integration harness server currently validates raw TCP echo, raw UDP echo, and plain HTTP over the tunneled stream path. It does not yet cover TLS, ENet, RTSP, or multi-packet media behavior.
- The host live Moonlight probe now confirms the real Sunshine path through SWG for tunneled `/resume` plus encrypted RTSP `OPTIONS` on `rtspenc://...`, but it still does not cover the full RTSP stage (`DESCRIBE`, `SETUP`, `PLAY`) or downstream media/control establishment. A Switch `STAGE_RTSP_HANDSHAKE` timeout can therefore still be a later Moonlight handshake issue rather than a raw tunnel transport failure.
- The sysmodule now logs per-`StreamControl` tunnel handle lifecycle for both TCP streams and ENet-style datagrams, including send/receive counts, sparse empty-poll traces, and close summaries. That should show whether Switch Moonlight sent control traffic and whether SWG delivered replies, but `rtspenc://` payloads still stay opaque at the sysmodule layer.
- Moonlight-Switch now compiles with a Switch-only bridge for HTTPS control, stream-host DNS, TCP stream sockets, UDP media sockets, and ENet control sockets, but none of that new transport path has been validated on hardware yet.
- The generic compat bridge now builds for a second non-Moonlight consumer in the Switch integration app, but those route decisions still need real on-device validation against a live profile.
- The runtime compat bridge now opens app sessions with identity only and relies on `[app_policy.*]` config for route behavior; misconfigured policies can change direct-vs-tunnel behavior without any source change in the consuming app.
- The SDK now owns the Moonlight bridge implementation, but third-party apps still need small source-level hook points to call the exported C/C++ bridge surface; full build-time interposition of unmodified upstream socket calls is not implemented yet.
- The sysmodule NPDM is intentionally permissive in Phase A (`service_access = ["*"]`) and should be tightened once the exact service dependencies are fixed.
